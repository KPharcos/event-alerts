2
3Users describe what they care about in plain text ("tell me if a big quake hits Japan").
4A cron job pulls events from free public feeds, Claude Haiku decides which alerts each
5new event matches, and matches are delivered by email and/or Slack. Admins manage
6users, alerts, events and the notification log in Django admin.

40## Sources
41
42- `usgs`: USGS earthquakes of magnitude 4.5+ from the last day (category `disaster`).
43- `rss`: each feed in `EVENT_RSS_FEEDS`, BBC World by default (category `news`). One failing feed doesn't skip the others.
44- `gdacs`: GDACS global disaster alerts — floods, cyclones, volcanoes, droughts, wildfires (category `disaster`).
45 GDACS earthquakes are skipped because USGS already covers them.
46
47There is no market feed. Market events (category `market`) are added by hand in admin
48(`/admin/alerts/event/add/`). Use any source name that isn't a feed key (e.g. `manual`) and an external id that is unique for that source. Admin-added events are matched and delivered on the next poll run, whatever their date.
49
50## Polling
51
52Run the poller from cron every 5 minutes. Cron doesn't load your shell environment, so put the
53variables above in a wrapper script or in the crontab itself, and keep a log:
54
55```
56*/5 * * * * cd <dir> && flock -n ~/poll_events.lock uv run python manage.py poll_events >> ~/poll_events.log 2>&1
57```
58
59`flock -n` skips a run while the previous one is still going (a slow Claude call can take
60minutes), so two runs never overlap. A crash between sending a notification and recording it
61can still send it again on the next run.
62
63Each run fetches every source, stores new events (deduplicated by source + external id),
64asks Claude once per unmatched event which active alerts it satisfies, sends to each matched
65alert's channels and records a `Notification` per channel. Only feed events from the last 24
66hours are matched and sent; older ones are marked done without a Claude call or a notification,
67so a first deploy or an outage doesn't send old news. If a Claude call fails with any API error,
68the event stays unmatched and is retried on the next run. After 3 failed calls in a row, a run
69stops matching and the rest waits for the next run. A failing source or channel is logged and
70does not stop the run.
71
72Failed sends are retried automatically: each run re-sends every `failed` notification from an
73earlier run in the last 24 hours, up to 3 attempts in total (`attempts` column in the admin notification log).
74After the third failure it stays `failed`.
75
76The first run after setup stores everything currently in the feeds. Only the recent events get a
77Claude call; the rest are marked done.

17## Intent
18
19**Problem:** Users want to be notified when something important happens in the world (breaking news, market moves, natural disasters) by email and Slack, with room for more channels later, and admins need a view to manage it. Nothing exists yet — the project is empty.
20
21**Approach:** New Django + SQLite app. A cron-run command polls free public feeds into `Event` rows; for each new event one Claude Haiku 5.5 call decides which users' free-text alerts it matches; matches are delivered through a channel registry (email, Slack incoming webhook) and logged. Admin creates users and manages everything in Django admin; logged-in users manage their own alerts on simple pages.
22
23## Boundaries & Constraints
24
25**Always:**
26- Stack: Python 3.12+, Django 6.x, SQLite, `anthropic` SDK, managed with `uv` (`pyproject.toml`). No other runtime dependencies (stdlib `urllib`, `xml.etree`, `csv`, `json` for feeds and Slack).
27- Alerts are free text ("tell me if a big quake hits Japan"). Matching uses model `claude-haiku-5-5`, one API call per new event covering all active alerts, structured output returning matched alert ids. Ids not in the active set sent to that call are ignored.
28- Event text from feeds is untrusted: prompt tells the model to treat it as data only.
29- Channels live in one registry (key → send function + target validation). Adding a channel = one function + one registry entry; no model or matcher changes.
30- Slack target must be an `https://hooks.slack.com/` URL (validated on save, prevents SSRF). Email target must be a valid email.
31- An event is never notified twice to the same alert channel (DB unique constraint).
32- One failing source, channel send, or event never aborts the whole poll run.
33- Users only see and edit their own alerts. No public sign-up; admin creates users.
34- Secrets/config from environment: `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, email SMTP settings, `ANTHROPIC_API_KEY` (read by SDK).
35
36**Never:**
37- No sign-up page, digests, custom admin dashboard, Slack OAuth app, Celery/queues, REST API, paid feed APIs, frontend framework.
38- No keyword/category pre-filter in front of the AI matcher.
39- No network calls in tests (mock Claude, feeds, Slack).

226## Conventions
227
228- Registries as dicts: `CHANNELS` (delivery), `SOURCES` (feeds). Extend by adding one entry.
229- Failure isolation everywhere: per source, per RSS feed, per event, per send. Errors are logged, not raised.
230- `deliver()` and `match_event()` return values instead of raising; `None` from the matcher means "retry later".
231- Untrusted text is escaped at each output: XML in the prompt, Slack `& < >`, Django autoescape in templates.
232- Known limits are marked in code with `# shortcut: <limit>, <when to upgrade>`.
233- Settings come from env vars with safe defaults; Django 6.1 `MAILERS` instead of `EMAIL_BACKEND`.
234- Tests: `PollTestBase` patches `alerts.channels._opener.open` (Slack); `claude_returning(ids)` / `claude_raising(exc)` patch the Anthropic client; `poll(sources_map)` swaps `SOURCES`; email uses `mail.outbox`. No network in tests.

236## Gotchas
237
238- **24 h window:** feed events (source in `SOURCES`) older than 24 h are marked matched without a Claude call or a send, with a warning count. Events from any other source (admin-added) always match. Matching runs newest first.
239- **Retries ignore the matcher:** failed sends are retried even when the circuit breaker tripped. Retries skip inactive alerts and users, only cover notifications from the last 24 h, and go to the channel's *current* target.
240- **Crash window:** `Notification` is created after `deliver()`, so a crash between them resends next run (`flock` only prevents overlap).
241- **Description cap is form-level:** user form and admin enforce 2000 chars; direct ORM writes don't.
242- **Choices from the registry:** adding a channel changes `AlertChannel.channel` choices, so run `makemigrations` (no schema change).
243- **Alerts snapshot once per run:** an alert created mid-run waits for the next run. With no active alerts, new events are marked matched and never revisited.
244- **400s retry:** a permanently rejected prompt stalls matching (an error logged each run, up to 3 calls per run) instead of dropping events.
245- **Deployment:** set `DJANGO_CSRF_TRUSTED_ORIGINS` behind an HTTPS proxy and run `collectstatic`. Secure cookies and HSTS are not set.
246- **`httpx2`** is imported by tests but only installed transitively via `anthropic`.
247- `item.pop("external_id")` mutates source dicts: fetchers must return fresh dicts.
