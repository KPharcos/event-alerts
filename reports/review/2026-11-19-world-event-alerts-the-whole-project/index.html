Overview

Where this change sits

A greenfield Django 6.1 + SQLite app (the repository was empty before the first commit). Users write alerts in plain text ("tell me if a big quake hits Japan"). A cron job runs poll_events every 5 minutes: it pulls free public feeds into Event rows, asks Claude Haiku once per new event which alerts it satisfies, and sends each match through a channel registry (email, Slack webhook), logging every send as a Notification. Admins run everything from Django admin; users manage only their own alerts on three small pages.

Green is new; everything in this report is new code, so the whole flow is green.

Why this change

The request: users want to be told when something important happens in the world (breaking news, market moves, natural disasters) by email and Slack, with room for more channels later, plus an admin view. Choices were made interactively with the owner and are recorded in the spec's change log: Django + SQLite, free feeds only (the Stooq market feed was dead, so market events are added by hand), free-text alerts matched by Claude Haiku 5.5, a Slack incoming webhook per alert, admin-created users, immediate delivery, automatic retries (3 attempts), and only events from the last 24 hours notify.

What changes

Everything runs in one management command; there is no queue or worker. Two dictionaries are the extension points: SOURCES (feed fetchers) and CHANNELS (send + validate per channel). The matcher puts all active alerts into one prompt and asks for structured output (MatchResult.alert_ids); returned ids are intersected with the active set. Failure is isolated at every level: per source, per RSS feed, per event, per send. Any Claude API error leaves the event for the next run; three failures in a row stop matching for that run. A unique constraint on (alert channel, event) plus an existence check stops duplicate sends. The trade-off taken: simplicity (one prompt, one process, SQLite) over scale; the one-prompt limit is marked in code with a shortcut: comment.

How to read this report

Follow the poll run: chapter 1 is the cron command and the tables it writes; chapter 2 where events come from; chapter 3 how Claude decides matches; chapter 4 how a match is delivered. Chapters 5 and 6 are the two ways people change data: the user pages and the admin. Tests sit with the code they prove. Open points from the reader pass: feed bodies are read without a size cap and parsed with the standard library XML parser rather than defusedxml (accepted in review because the feeds are fixed, well-known publishers); the GDACS test fixture's date says Wed for a Thursday (harmless, the weekday is ignored). The admin add-alert bug the first reader found is fixed in this diff (chapter 6, admin.py line 29).

Excluded as not-the-change: the README, CLAUDE.md and docs/ (prose), the BMAD spec, generated migrations, and Django's startproject boilerplate (manage.py, asgi.py, wsgi.py).

New terms

Event
One world event from a feed or added in admin. matched_at empty means it still has to be matched.
Alert / AlertChannel
A user's free-text description of what to be told about, and the targets (email address or Slack webhook URL) it is delivered to.
Notification
One delivery attempt record per (alert channel, event): sent or failed, with attempts and the error text.
SOURCES
Dict of feed name → fetcher in alerts/sources.py. Its keys are also the Event.source values that age out after 24 h.
CHANNELS
Dict of channel key → Channel(label, validate, send) in alerts/channels.py; the only place a new delivery channel is added.
Match window
MATCH_WINDOW (24 h): feed events older than this are marked done without a Claude call or a send. Owner's decision, so a first deploy or an outage doesn't send old news.
Circuit breaker
MAX_MATCH_FAILURES (3): after three failed events in a row a run stops matching and leaves the rest for the next run.
MAILERS
Django 6.1's email setting that replaces the old EMAIL_* settings; SMTP when EMAIL_HOST is set, console otherwise.

Chapters

  1. 1. One poll run: ingest, the 24-hour window, the match loop and retries 4 files, 29 notes

    The whole system is driven by poll_events, run by cron behind flock -n, so this comes first. One run has four phases: fetch every source into Event rows, mark old feed events done, match the rest newest first (stopping after three failures in a row), then re-send failed notifications from earlier runs. The models are here because this is the first code that writes them.

    An event leaves Unmatched once: aged out, or matched. A Claude failure keeps it for the next run.

  2. 2. Where events come from: USGS, RSS and GDACS 3 files, 13 notes

    Chapter 1 calls each fetcher in SOURCES; this chapter is those fetchers. Each returns plain dicts of Event fields, all HTTP goes through _get (15 s timeout), and RSS-shaped feeds share one parser. Untrusted feed text is normalised here: dates made timezone-aware, HTML stripped, sizes capped.

  3. 3. How Claude decides which alerts an event matches 4 files, 12 notes

    For each event that survives the window, chapter 1 calls match_event. It sends one Claude Haiku request with the event and every active alert, asks for structured output, and maps every outcome to "these ids", "no ids" or "retry later". The routing table below is what the poller depends on.

    Only the first branch keeps the event unmatched; every other outcome marks it done.

  4. 4. Delivering a match: the channel registry, email and Slack 3 files, 12 notes

    After a match, chapter 1 calls deliver, which looks the channel up in CHANNELS. This chapter is that registry and the two channels. Slack is where untrusted text meets an outbound HTTP request, so it carries the escaping and the SSRF guard; email depends on the MAILERS setting shown with it.

  5. 5. Users manage their own alerts 11 files, 21 notes

    Everything so far reads Alert and AlertChannel; this chapter is how users create them. Three function views behind login_required, one form plus an inline formset for channels, and minimal templates. Web-stack settings (hosts, CSRF origins, static files, the secret key) sit here because the web pages are what use them.

  6. 6. The admin view 2 files, 7 notes

    The other way data changes is Django admin, where admins create users, alerts, channels and manual events and read the delivery log. It reuses the user form and channel formset so the same limits apply, and it makes the notification log read-only.
